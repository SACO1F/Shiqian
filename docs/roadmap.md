## 2. 后续开发应关注的角度

### 2.1 整理动作是否足够轻

主流程应当保持为“发现文件 → 顺手标注 → 日后快速找回”。浮窗是这一流程的主要入口，后续价值首先来自减少操作步骤和不打断当前工作。

优先观察：标签是否容易找到、拖动后是否能确定标注对象、预设是否便于调整、浮窗是否遮挡工作、关闭与返回行为是否符合预期。

### 2.2 标注是否长期跟得住文件

文件改名、整理到另一个文件夹、移动磁盘或暂时离线时，标签和备注不应轻易失联。

下一步从用户明确选择的目录监听开始，利用现有文件身份识别能力处理可以可靠确认的移动／改名；无法确定时提示重新关联，避免把旧标注挂到同名的新文件上。

### 2.3 文件量增长后还能否快速找到

随着资料增多，单纯不断增加标签会产生同义词、重复分类和过多筛选操作。需要逐步增加标签合并、常用标签排序、标签组合与智能集合。

智能集合保存的是查询条件，例如“品牌升级 + 参考素材 + 图片”，以后点击集合即可得到当前匹配结果。

### 2.4 浏览器与桌面是否共用同一套资料

浏览器插件的价值在于发现网页内容时立即保存来源和标签。它应继续使用桌面端的标签身份与资料库，避免出现两套名称相同却不同步的标签。

先跑通网页链接和文字摘录，再加入网页图片副本；图片副本会带来下载、存储、去重、备份与删除责任，不能简单塞入当前“只引用原文件”的模型。

### 2.5 功能完成后能否可靠交付

每个阶段都需要明确退出条件：测试什么、哪些环境通过、旧数据如何升级、失败如何恢复、交付哪个安装包。

应建立版本控制、可重复构建和发布记录；将测试临时目录与真实用户资料库持续隔离。发布 ZIP 是交付快照，日常开发只修改主源码目录。

## 3. 建议迭代顺序

以下为原建议路线。v0.2.1 根据新增需求先交付图片浏览与导航改进，原表中的浮窗稳定性事项仍待完成；后续版本号与工期需随实际范围调整。

| 阶段 | 主要目标 | 建议内容 | 完成条件 |
| --- | --- | --- | --- |
| 下一轮稳定性迭代（原计划 v0.2.1） | 浮窗稳定、便于日常使用 | 完整拖拽实测；多屏／缩放校验；保存浮窗位置与折叠状态；改进拖动反馈；明确退出入口 | 能稳定完成桌面／资源管理器／拾签内标注；无效目标不写入；重启与显示器变化后浮窗仍可找回 |
| v0.3 | 提升本地整理和查找效率 | 预设排序；标签合并；智能集合；选定目录监听；按需补托盘与全局快捷键 | 常用整理流程减少重复操作；合并不丢关联；可靠移动可跟踪，不确定的变动可恢复 |
| v0.4 | 浏览器协同最小版本 | 统一资料模型和迁移；本地桥接；网页链接／文字摘录采集；共享标签；断线队列 | 浏览器保存后桌面可查；断线后重试不重复、不丢任务；旧文件标签和备注迁移正确 |
| v0.5 | 网页图片采集与来源管理 | 用户主动保存图片；来源页面；受管理图片副本；扩展搜索；新版备份 | 能区分“只保存来源”和“原图已保存”；备份可以恢复受管理原图和标注 |
| 后续增强 | 内容级检索与精细标注 | 图片框选／局部备注、OCR；需求明确后再评估 AI 建议和语义检索 | 有具体使用场景与可验证收益；成本、处理时间和误判反馈可接受 |

v1.0 应以稳定性、数据恢复、安装升级和目标环境验收完成为条件，不以累计增加多少功能作为标准。

## 4. 下一轮具体工作清单：v0.2.1

### A. 先建立真实验收样本

- 桌面与资源管理器：图标／列表视图、中文名称、较长名称、隐藏扩展名、多个同名文件。
- 拾签内部：网格、列表、筛选结果、弹窗遮挡下的命中与拒绝。
- 多显示器及常见缩放：100%、125%、150%，显示器之间移动浮窗后再次标注。
- 原生文件批量拖入标签，观察准确数量、失败反馈以及撤销对象。
- 无效目标、取消、鼠标快速移动与松开、资源管理器切换标签页。

验收重点：实际命中的文件就是用户看到的目标；空白处、目录或无法唯一识别的对象不会产生错误标注。记录复现步骤与环境，优先修复阻断问题。

### B. 完善浮窗的日常体验

- 保存位置和折叠状态；显示器拔出或布局变化后，将浮窗恢复到可见工作区。
- 允许调整预设顺序；展示长标签的完整名称，保持键盘可操作。
- 对有效目标、无效目标、成功和失败提供可区分反馈，明确文件、标签、数量与当前可撤销的操作。
- 梳理隐藏、关闭、返回工作台和退出程序；避免用户不清楚应用是否仍在运行。

### C. 补齐发布验收

- 在干净环境验证安装、启动、卸载和重新安装。
- 从已有 v0.1.0／v0.2.0 数据升级，核对文件记录、标签、备注、收藏与预设。
- 验证备份恢复，原文件缺失或磁盘不可用时能解释状态并保留标注。
- 固定一个交付构建，记录测试覆盖与未覆盖场景，打包版本和源码快照保持一致。

这一轮完成后再扩大功能范围，避免同时修改原生拖拽、文件监听和浏览器数据模型，导致问题来源难以定位。

## 5. 浏览器插件开发的前置工作

沿用已有 [浏览器协同规格](browser-extension-design-v0.2.md)，但按小阶段交付。

1. **统一资料模型。** 当前主要对象为本地文件；新增网页与摘录对象，标签和备注统一关联，保留现有稳定 ID 与来源信息。
2. **数据迁移。** 升级前备份；迁移后核对记录与关联数量；旧版本客户端对新数据库拒绝写入。
3. **通信契约。** 按现有 Native Messaging 设计明确版本握手、授权来源、请求 ID、错误类型和幂等规则；扩展不直接写 SQLite。
4. **最小闭环。** 扩展采集网页链接与选中文本，选择标签，桌面立即检索；关闭桌面服务时保留可恢复的队列。
5. **图片副本。** 最小闭环稳定后再加入图片获取与受管理存储，同时升级备份语义。

浏览器协同设计文档中的“v0.2”是文档版本，不表示浏览器插件已经随着桌面 v0.2.0 实现。

## 6. 日常开发进程

每轮采用同一流程：明确场景与验收样例 → 拆成小任务 → 实现 → 针对改动验证 → 更新文档与进度 → 打包体验 → 根据实际反馈决定下一轮。

任务状态建议统一为：待开发、开发中、待验证、已完成。涉及 Windows 原生交互的任务必须保留“待验证”阶段，不能仅以构建成功关闭任务。

建议记录：完成的验收场景、当前阻断问题、数据兼容性变化、下一步工作。无需为尚未确定的长期功能给出完成率。
